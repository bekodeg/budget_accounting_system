# 5. Отчеты, экспорт и фискальные документы

## 5.1. Отчет за месяц

Показывает:

- доход за месяц;
- расход за месяц;
- итоговый cash flow;
- расход по категориям;
- план / факт / остаток по категории;
- остаток по каждому счету;
- вклад каждого автора при необходимости аудита.

Формула остатка плана категории:

`remaining = planned_expense - actual_expense`

Месячный отчет строится реактивно одним локальным SQL-потоком по периоду
`[month_start, next_month_start)`. Soft-deleted операции исключаются, а переводы
не входят в income/expense/cash flow.

План хранится без отдельного currency-поля и интерпретируется в
`budgets.base_currency`. Поэтому:

- income/expense/cash flow сохраняются раздельно по валютам;
- факт категории также хранится раздельно по валютам;
- `remaining` сравнивает план только с фактом в базовой валюте бюджета;
- автоматическая FX-конвертация не выполняется.

Это не позволяет случайно сложить, например, EUR и USD в одно число.

Остатки счетов в выбранном месяце рассчитываются на конец периода:
учитываются операции с `occurred_at < next_month_start`, включая переводы.
Архивные счета остаются видимыми в историческом отчете.

Категория попадает в отчет, если для нее есть план или фактический расход.
Поддерживаются оба крайних случая: план без факта и факт без плана.
Расход без категории отображается как «Без категории».

Вклад авторов не выводится в S3: текущий этап однопользовательский. Поле
`author_id` уже сохраняется в транзакциях и может быть добавлено отдельной
группировкой на этапе совместного бюджета без изменения исходных данных.

## 5.2. Отчет за год

Группировка по месяцам и категориям:

- доходы;
- расходы;
- net cash flow;
- план;
- факт;
- отклонение.

Годовой отчет строится SQL-агрегациями за полуинтервал
`[January 1, January 1 next year)`. В domain-модели всегда присутствуют все
12 месяцев, включая пустые. Годовые income/expense/net вычисляются как сумма
месячных агрегатов, поэтому годовой итог проверяемо совпадает с их суммой.

План и variance считаются в `budget.base_currency`; фактические расходы в
других валютах сохраняются отдельно и не конвертируются автоматически.

## 5.3. Произвольный период

Параметры:

- `date_from`;
- `date_to`;
- optional `category_ids`;
- optional `account_ids`;
- optional `author_ids`.

Границы имеют строгую семантику `[date_from, date_to)`: нижняя граница
включается, верхняя исключается. Пустой или обратный период запрещен на уровне
domain-фильтра.

Каждый из фильтров принимает множество идентификаторов. Непустые множества
комбинируются через AND, а значения внутри одного множества — через SQL IN.
Фильтрация выполняется в SQLite до GROUP BY; полная история транзакций в Dart
не загружается.

Текущий однопользовательский UI показывает author-фильтр как «Только мои»,
но repository/application API уже поддерживает произвольный набор
`author_ids` для будущего multi-user режима.

Отчет строится полностью локально SQL-агрегациями и сохраняет валюты
раздельно.

## 5.4. Расчет остатка счета

Для счета без переводов:

`balance = opening_balance + income - expense`

При поддержке переводов:

`balance = opening_balance + income + incoming_transfers - expense - outgoing_transfers`

## 5.5. CSV

Рекомендуемые колонки экспорта транзакций:

```text
transaction_id,date,type,amount,currency,author,account,category,description
```

Числовой формат должен быть машинно-однозначным; локализованное отображение выполняется только в UI.

## 5.6. XLSX

Минимально три листа:

1. `Summary` — итоги;
2. `By Category` — план/факт;
3. `Transactions` — детализация.

## 5.7. Создание транзакции из QR

Поток:

```mermaid
flowchart LR
    S[Скан QR] --> P[Parse payload]
    P --> D[Черновик транзакции]
    D --> U[Пользователь проверяет категорию/счет]
    U --> T[Сохранение транзакции]
```

Если QR содержит дату и сумму, они подставляются автоматически. Продавец/назначение может попасть в описание.

## 5.8. Создание транзакции из фото чека

Поток:

```mermaid
flowchart LR
    I[Фото чека] --> Q{QR найден?}
    Q -->|Да| P[Parse QR]
    Q -->|Нет| O[On-device OCR]
    P --> D[Draft]
    O --> D
    D --> V[Проверка пользователем]
    V --> T[Transaction]
```

Предпочтение отдается локальному распознаванию, чтобы базовый сценарий не зависел от backend.

## 5.9. Ограничение фискального импорта

Некоторые фискальные QR-коды содержат только реквизиты для поиска документа, а полная детализация доступна через внешний сервис. В архитектуре это оформляется как **опциональный client-to-provider adapter**: мобильное приложение обращается к провайдеру напрямую, когда есть интернет. Собственный сервер системы для этого не требуется.

При отсутствии интернета приложение все равно должно:

- сохранить исходный QR/фото;
- извлечь доступные локально дату/сумму;
- создать черновик;
- завершить enrich позже либо дать пользователю заполнить поля вручную.
