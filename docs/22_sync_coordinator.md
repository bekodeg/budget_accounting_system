# 22. Coordinator topology для multi-peer sync

## 22.1. Цель

Для нескольких участников используется временный coordinator вместо full mesh.
Coordinator не хранит отдельное authoritative state: он использует тот же локальный
sync journal, что и остальные устройства.

## 22.2. Выбор coordinator

Из доступных device_id выбирается лексикографически минимальный идентификатор.
При одинаковом наборе peers все участники получают одинаковый результат независимо
от порядка discovery.

## 22.3. Fan-in / fan-out

Сессия выполняется в два прохода:

1. fan-in: coordinator синхронизируется с каждым доступным peer и собирает union
   подписанных operations;
2. fan-out: coordinator повторно синхронизируется с доступными peers и раздает
   накопленный union.

Каждая pairwise-сессия использует существующий state-vector protocol, поэтому
повторный проход передает только реально недостающие операции.

## 22.4. Ограничение соединений

SyncCoordinatorService ограничивает число одновременно выполняемых pairwise sessions
параметром maxConcurrentConnections. Значение по умолчанию — 4.

Это предотвращает sync storm и не требует полного mesh между 20 участниками.

## 22.5. Failover

Если coordinator становится недоступен:

1. он удаляется из набора доступных peers;
2. выполняется повторный детерминированный election;
3. сессия продолжается с новым coordinator.

Потеря обычного peer не останавливает остальных участников.

Данные не теряются, потому что каждая успешно завершенная pairwise sync уже
зафиксировала полученные operations в локальном journal.

## 22.6. Тестирование

Unit/multi-peer simulation покрывает:

- одинаковый election при разном порядке discovery;
- сходимость четырех peers через fan-in/fan-out;
- ограничение конкурентных соединений;
- потерю coordinator и re-election;
- потерю отдельного peer без остановки сессии.

Manual multi-device soak test остается частью приемочного этапа S6.
