# 15. Issues, ошибки и ветки исправлений

Этот документ задает единый процесс регистрации и обработки ошибок, найденных разработчиком, CI, тестировщиком или заказчиком.

Цель процесса — чтобы по любой ошибке можно было ответить на четыре вопроса:

1. в какой версии она обнаружена;
2. как ее воспроизвести;
3. каким изменением она исправлена;
4. на каком этапе исправление проверено и выпущено.

## Формат Issue

### Плановая задача

Для плановых задач сохраняется существующий формат:

```text
[S<stage>][P<priority>] <краткое действие>
```

Примеры:

```text
[S3][P0] Реализовать месячный отчет план/факт
[S4][P1] Реализовать первичную синхронизацию нового устройства
```

### Ошибка

Для дефекта используется формат:

```text
[BUG][P<priority>] <наблюдаемый симптом>
```

Заголовок должен описывать наблюдаемую проблему, а не предполагаемую техническую причину.

Хорошо:

```text
[BUG][P1] Баланс счета не обновляется после перевода
```

Плохо:

```text
[BUG] Ошибка в AccountRepository
```

Техническая причина может оказаться другой и должна быть зафиксирована после диагностики.

## Приоритет ошибки

| Приоритет | Когда использовать | Влияние на выпуск |
| --- | --- | --- |
| `P0` | потеря/повреждение данных, нарушение конфиденциальности, приложение не запускается, критический сценарий полностью недоступен без обхода | продвижение версии останавливается до исправления |
| `P1` | неверный финансовый результат, сломан основной пользовательский сценарий, частые crash/error без приемлемого обхода | версия с ошибкой не продвигается в `main` |
| `P2` | заметная функциональная ошибка, но есть приемлемый обход и данные не повреждаются | исправляется в обычном цикле |
| `P3` | косметика, тексты, некритичное поведение интерфейса | не блокирует выпуск |

Если приоритет неясен, выбирать более высокий до завершения первичной диагностики, затем явно изменить его в Issue.

## Обязательное содержимое bug Issue

Описание ошибки должно содержать:

```markdown
## Где обнаружено
- Build / tag:
- Commit, если известен:
- Ветка/окружение: dev | stage | main
- Устройство:
- ОС и версия:

## Предусловия
Что должно существовать до воспроизведения ошибки.

## Шаги воспроизведения
1.
2.
3.

## Фактический результат
Что произошло.

## Ожидаемый результат
Что должно было произойти.

## Повторяемость
Всегда / иногда / один раз.
Если иногда — примерная частота и известные условия.

## Влияние на данные
Нет / неверное отображение / риск потери / потеря или повреждение данных.

## Материалы
Логи, обезличенные скриншоты или минимальный тестовый пример.

## Критерии приемки
- [ ] причина локализована;
- [ ] добавлен regression test, если это технически возможно;
- [ ] исправление прошло локальные проверки;
- [ ] исправление проверено на stage;
- [ ] существующие пользовательские данные сохраняются при обновлении, если изменение затрагивает БД.
```

Если ошибка пришла от заказчика, обязательно указывать точный release tag или версию приложения. Формулировки вроде "последняя версия" недостаточны.

## Конфиденциальность

Репозиторий и его Issues могут быть доступны шире, чем данные заказчика.

Нельзя прикладывать к Issue:

- реальные финансовые данные заказчика;
- полную пользовательскую SQLite-базу;
- пароли, ключи подписи и GitHub Secrets;
- персональные данные, не требуемые для воспроизведения;
- скриншоты с неанонимизированными счетами, комментариями или именами.

Для воспроизведения использовать синтетические данные. Если нужен диагностический материал, он должен быть предварительно обезличен.

## Когда заводить отдельный Issue

Отдельный bug Issue обязателен, если ошибка:

- обнаружена в `dev`, `stage`, `main` или переданной заказчику сборке;
- является регрессией уже работавшего сценария;
- может влиять на данные;
- требует изменения вне текущей задачи;
- требует отдельного тестирования или отслеживания.

Если мелкая ошибка обнаружена внутри еще не слитой feature-ветки и относится непосредственно к реализуемой задаче, ее можно исправить в этой же ветке без отдельного Issue. Регрессии, проблемы данных и ошибки, уже попавшие в общую ветку, всегда оформляются отдельно.

## Формат веток

Рабочая ветка создается от актуального `dev`.

Используются форматы:

```text
feature/<issue>-<slug>
fix/<issue>-<slug>
chore/<issue>-<slug>
chore/<slug>
```

Где:

- `<issue>` — номер GitHub Issue без символа `#`;
- `<slug>` — короткое описание латиницей в lowercase kebab-case;
- slug должен описывать изменение, а не имя разработчика.

Примеры:

```text
feature/14-monthly-plan
fix/81-transfer-balance-not-updated
fix/82-transaction-edit-crash
chore/83-android-signing
chore/update-dependencies
```

Не использовать:

```text
fix-bug
my-branch
hotfix-final
test2
ivan/fix
```

Отдельный `hotfix/*` поток не используется. Даже P0/P1 проходит через существующую цепочку:

```text
fix/<issue>-<slug> -> dev -> stage -> main
```

Это сохраняет одинаковые проверки и исключает выпуск непроверенного исправления напрямую в `main`.

## Процесс обработки ошибки

### 1. Зарегистрировать и воспроизвести

Создать Issue и заполнить известные данные.

До изменения кода подтвердить воспроизведение на указанной версии. Если воспроизвести не удалось, Issue остается открытым, а в комментарии фиксируются проверенные условия и недостающая информация.

### 2. Определить приоритет

Оценить влияние на данные и основной пользовательский сценарий.

Для `P0` и `P1` остановить продвижение затронутой версии из `stage` в `main` до исправления и повторной проверки.

### 3. Создать ветку

От актуального `dev`:

```bash
git checkout dev
git pull
git checkout -b fix/<issue>-<slug>
```

Пример:

```bash
git checkout -b fix/81-transfer-balance-not-updated
```

Не исправлять дефект прямым коммитом в `dev`, `stage` или `main`.

### 4. Зафиксировать регрессию тестом

По возможности сначала добавить тест, который воспроизводит ошибку и падает на старом поведении.

Для ошибок данных или Drift schema дополнительно нужен migration/data-integrity test, который создает старую схему с данными, выполняет миграцию и проверяет сохранность бизнес-данных.

Если автоматический regression test технически невозможен, причина должна быть указана в PR, а ручной сценарий проверки — описан явно.

### 5. Исправить минимальную причину

Исправление должно быть ограничено областью дефекта. Несвязанный refactoring и новую функциональность следует выносить в отдельные задачи, чтобы bugfix можно было проверить и при необходимости откатить независимо.

### 6. Выполнить локальные проверки

Минимальный набор перед PR:

```bash
flutter pub get
dart run build_runner build --delete-conflicting-outputs
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
```

Для изменений схемы БД выполнить также Drift migration workflow.

### 7. Создать PR в dev

PR создается:

```text
fix/<issue>-<slug> -> dev
```

Рекомендуемый заголовок:

```text
fix: <краткое описание исправления>
```

В описании PR обязательно указать:

```markdown
Refs #<issue>

## Причина
Корневая причина ошибки.

## Исправление
Что изменено.

## Проверка
Какие автоматические и ручные проверки выполнены.

## Риск
Какие соседние сценарии могут быть затронуты.
```

Issue не закрывается сразу после merge в `dev`: код еще не прошел полный Stage CI и ручную проверку сборки.

### 8. Проверить на stage

После merge в `dev` исправление продвигается обычным PR:

```text
dev -> stage
```

На `stage` должны успешно пройти полный CI и необходимые ручные сценарии.

При проверке ошибки используется тот же сценарий, который был записан в Issue. Для регрессии дополнительно проверяется соседний основной сценарий.

Если ошибка сохраняется, Issue остается открытым; новое исправление снова выполняется через отдельную `fix/<issue>-<slug>` ветку от актуального `dev`.

### 9. Выпустить и закрыть

После успешной проверки `stage -> main` выполняется штатным promotion-процессом.

Bug Issue закрывается после того, как:

- исправление проверено на `stage`;
- версия с исправлением попала в `main`/release;
- в Issue указан release tag или commit, содержащий исправление.

Для ошибки, сообщенной заказчиком, после выпуска фиксируется версия, которую нужно установить для повторной проверки.

## Ошибка, обнаруженная на stage

Не исправлять `stage` напрямую.

Порядок:

```text
bug on stage
    |
    v
create Issue
    |
    v
fix/<issue>-<slug> from dev
    |
    v
PR -> dev
    |
    v
PR dev -> stage
    |
    v
full Stage CI + regression check
```

Так `dev` остается источником всех последующих изменений, а `stage` — только проверяемым кандидатом.

## Ошибка, обнаруженная заказчиком

1. запросить release tag/версию приложения, модель устройства и версию ОС;
2. записать точные шаги и ожидаемое поведение;
3. определить, затронуты ли уже сохраненные данные;
4. создать `[BUG][P…]` Issue без чувствительных данных;
5. воспроизвести на той же версии;
6. исправить через `fix/<issue>-<slug> -> dev -> stage -> main`;
7. проверить обновление поверх предыдущей версии, если меняется БД или startup logic;
8. передать заказчику новый release tag для повторной проверки;
9. закрыть Issue после подтвержденного исправления или внутренней приемки релиза.

## Definition of Done для bugfix

Bugfix считается завершенным, когда одновременно выполнено следующее:

- Issue содержит воспроизводимый сценарий или задокументированную причину невозможности воспроизведения;
- причина ошибки установлена;
- добавлен regression test либо объяснено, почему он невозможен;
- локальные проверки проходят;
- PR в `dev` влит;
- Stage CI проходит;
- ручной сценарий воспроизведения больше не приводит к ошибке;
- если затронута БД, migration/data-integrity test подтверждает сохранность данных;
- исправление выпущено через `main`;
- Issue содержит ссылку на исправляющий PR/release и закрыт.
