# ADR-001: Local-first P2P вместо backend-сервера

- Status: Proposed
- Date: 2026-09-15

## Context

Система должна одновременно удовлетворять требованиям:

- несколько пользователей редактируют один бюджет;
- до 20 одновременных пользователей;
- работа без доступа к интернету;
- отсутствие backend-сервера.

## Decision

Использовать local-first архитектуру:

1. Полная рабочая копия бюджета хранится на каждом устройстве в SQLite.
2. Все изменения фиксируются локально и не блокируются сетью.
3. Репликация выполняется P2P между устройствами.
4. Для групповой sync-сессии выбирается временный coordinator.
5. Конфликты разрешаются детерминированным field-level LWW на основе Lamport clock + device ID.
6. Удаления распространяются как tombstone.

## Consequences

### Positive

- приложение полностью работоспособно offline;
- нет затрат и эксплуатации backend;
- нет единой точки отказа;
- отчеты быстрые и локальные;
- данные по умолчанию остаются на устройствах участников.

### Negative

- мгновенная синхронизация невозможна, если между устройствами нет канала связи;
- сложнее управление конфликтами и удалением участников;
- discovery и P2P на iOS/Android требуют отдельного тестирования;
- резервное копирование становится ответственностью клиента;
- отзыв доступа не может стереть уже полученную ранее локальную копию данных с чужого устройства.

## Rejected alternatives

### Central backend
Проще синхронизация, но нарушает требование отсутствия сервера.

### Shared cloud drive/file
Не требует собственного backend, но обычно зависит от интернета/стороннего облака и имеет слабую конкурентную запись.

### Full mesh P2P
Просто концептуально, но плохо масштабируется по числу соединений и расходу батареи при 20 участниках.
